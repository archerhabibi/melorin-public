## محدودیت صادقانه‌ی این Review

بند 5 صریحا "Review امنیتی مستقل" خواسته. من (همان مدلی که پچ 3.2.5 را
ساخت) نمی‌توانم واقعا "مستقل" باشم - یک انسان یا مدل دیگر باید این پچ
را هم جدا بررسی کند. آنچه در ادامه آمده یک self-audit دقیق و
Checklist-محور است در برابر معیارهای مشخصی که خود Roadmap لیست کرده،
نه جایگزینی برای Review واقعی توسط یک طرف مستقل.

## یافته‌ی اصلی: Login/Link CSRF (رفع شد)

پیاده‌سازی 3.2.5 در برابر یک حمله واقعی محافظت نداشت:

1. HMAC روی *محتوای* callback تلگرام است (id, first_name, auth_date, ...)
   - نه روی "این‌که چه کسی قصد وصل‌کردن این تلگرام را دارد".
2. یک مهاجم می‌تواند از طریق ویجت رسمی تلگرام، برای *حساب تلگرام خودش*
   یک callback URL کاملا معتبر و امضاشده بگیرد - این کار هیچ رازی لازم
   ندارد، هرکسی می‌تواند برای خودش این را بگیرد.
3. اگر این URL را برای قربانی بفرستد و قربانی *در حالی که به یک حساب
   Melorin دیگر لاگین است* روی آن کلیک کند، سرور (بدون این رفع) تلگرام
   مهاجم را به حساب قربانی وصل می‌کرد - چون تنها چیزی که چک می‌شد
   اعتبار HMAC بود، نه اینکه این callback واقعا از همین Session/درخواست
   شروع شده یا نه.

این دقیقا همان دسته حمله‌ای است که پارامتر state در OAuth/به طور کلی
Login-widget ها برایش طراحی شده (CSRF کلاسیک روی یک Callback).

### رفع

- `CompleteProfileController::show` یک state تصادفی (`random_bytes(16)`)
  می‌سازد، در Session ذخیره می‌کند، و در `data-auth-url` ویجت به
  Query String اضافه می‌کند.
- `TelegramLinkController::callback` قبل از هر بررسی دیگری (حتی قبل
  از verify کردن HMAC)، `state` را از Session با `pull()` می‌خواند
  (یعنی بلافاصله از Session حذف می‌شود - یک‌بارمصرف) و با
  `hash_equals()` با مقدار داخل query مقایسه می‌کند. مو به مو تطبیق
  نداشت → رد، بدون اینکه حتی HMAC چک شود.
- چون state با `pull()` حذف می‌شود، حتی خودِ کاربر اصلی هم نمی‌تواند
  همان لینک را دوبار (مثلا با Refresh) استفاده کند - باید صفحه‌ی
  complete-profile را دوباره باز کند تا state تازه بگیرد.

## Checklist باقی (طبق متن دقیق بند 5)

| مورد | نتیجه |
|---|---|
| HMAC واقعا با bot_token واقعی محاسبه می‌شود (نه مقدار ثابت/جعلی) | تایید شد - `hash('sha256', $botToken, true)`؛ اگر `$botToken` خالی باشد (کانفیگ نشده)، کنترلر قبل از رسیدن به Verifier رد می‌کند، پس هیچ حالتی با secret خالی محاسبه نمی‌شود |
| مقایسه‌ی hash ثابت‌زمانی است | تایید شد - `hash_equals()` |
| `auth_date` چک می‌شود (ضد Replay قدیمی) | تایید شد - حداکثر 24 ساعت |
| هیچ مسیر fallback ناامن (قبول بدون چک در صورت شکست چیزی) وجود ندارد | تایید شد - هر شرط رد `return redirect()->withErrors()` است، هیچ‌جا "ادامه بده چون..." وجود ندارد |
| Merge خودکار به یک Identity دیگر ممکن نیست | تایید شد - پچ 3.2.5 از ابتدا این را داشت (`ownedBy->id !== currentUser->id` رد می‌شود) |
| Login/Link CSRF | یافت شد، رفع شد (بالا) |
| Rate limiting روی این Endpoint | تایید شد - `throttle:20,1` از پچ 3.2.5 |
| این Endpoint فقط برای کاربر لاگین‌شده است (نه ثبت‌نام ناشناس) | تایید شد - داخل گروه `auth+store.customer` |

جدا) همین چک‌لیست را دوباره روی کد نهایی اجرا کند.
