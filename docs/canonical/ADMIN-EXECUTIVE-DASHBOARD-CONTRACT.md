# Admin Executive Dashboard Contract (B7.1)

> نسخه 1.0 · Parent: Master 2.8 / Website 1.9 / Reseller Dashboard 1.0 · وضعیت: CANONICAL
> دامنه: صفحه‌ی اصلی پنل ادمین پلتفرم (Filament، `/admin`).
> **بدون Migration، بدون Route جدید، بدون تغییر در Purchase/Provisioning/Refund/Wallet/Payment.** همه‌ی داده از جدول‌های موجود خوانده می‌شود.

## ED1. Core: `Admin\Dashboard\ExecutiveDashboardService` (فقط‌خواندنی)
- ورودی فقط بازه‌ی زمانی (`DashboardPeriod`) است؛ هیچ شناسه‌ای از Request خوانده نمی‌شود. Scope = کل پلتفرم (برخلاف `ResellerDashboardService` که به یک نماینده Scope می‌شود).
- **هیچ رکوردی نمی‌سازد/تغییر نمی‌دهد.** باز کردن صفحه نباید در DB بنویسد (تست نگهبان: شمارش Wallet/Order/Payment/AuditLog قبل و بعد؛ و اسکن سورس برای فعل‌های نوشتن).
- Aggregate در دیتابیس (`SUM/COUNT/GROUP BY`)؛ تعداد کوئری به تعداد سفارش‌ها وابسته نیست (تست). مبالغ همه `int` (Minor Unit)، بدون float.
- Core هیچ Route/Filament/Money-format نمی‌شناسد؛ ساخت URL و قالب‌بندی مبلغ کار Channel است (تست نگهبان).
- متدها: `summary()` (KPI بازه + بازه‌ی قبل)، `position()` (وضعیت لحظه‌ای)، `trend()` (روند روزانه)، `topResellers()`، `recentOrdersQuery()/recentOrders()`، `serverHealthQuery()`، `alerts()`، `resellerQueuePendingPayments()`.

## ED2. تعریف‌ها
| مفهوم | تعریف |
|---|---|
| فروش قطعی | سفارش `paid` یا `account_created` — **هم‌تعریف با Reports ادمین و داشبورد نماینده** |
| فروش | `SUM(COALESCE(main_price, customers_price, 0))` — آنچه مشتری پرداخته (دو ستون هرگز هم‌زمان پر نیستند، بند ۳۱) |
| درآمد پلتفرم | `SUM(COALESCE(main_price, reseller_price, 0))` — آنچه به ما می‌رسد (مستقیم: `main_price`؛ نمایندگی: `reseller_price`) |
| سود نمایندگان | فروش − درآمد پلتفرم (برای فروش مستقیم صفر) — **درآمد ما نیست** |
| فروش مستقیم / نمایندگی | `reseller_id` خالی / پر؛ سهم نمایندگی = درصد صحیح گردشده از فروش |
| تمدید | سفارشی با `renews_account_id` پر؛ خرید = سفارش − تمدید |
| سفارش ناموفق | `failed` یا `provision_failed` (بر پایه‌ی `created_at`) |
| نرخ شکست | ناموفق ÷ (فروش قطعی + ناموفق) به «در هزار» صحیح و گردشده؛ نمایش با یک رقم اعشار (۳۳۳ ⇒ ۳۳٫۳٪) بدون float |
| کاربر جدید | `users.created_at` در بازه (حذف‌شده‌ها نمی‌آیند) |
| سرویس جدید | `Account` غیرآزمایشی (`is_test=false`) ساخته‌شده در بازه |
| سرویس فعال / رو‌به‌انقضا | `Account::activeNow` غیرآزمایشی؛ رو‌به‌انقضا = انقضا تا ۷ روز آینده |
| سرور فعال | `server_panels.status=active`؛ «از کار افتاده/کند» از `health_status`؛ «پر» = `capacity` تعریف‌شده و `active_accounts_count ≥ capacity`؛ مصرف ظرفیت فقط روی سرورهای دارای ظرفیت |
| پیش‌پرداخت نزد پلتفرم | جمع موجودی‌های **مثبت** Wallet با `scope_key=main` (شامل اعتبار نمایندگان). Wallet فروشگاه نماینده تعهد خود نماینده است و نمی‌آید |
| بدهی نمایندگان | قدرمطلق جمع موجودی‌های **منفی** Wallet Main صاحبانِ نماینده |
| نماینده‌ی بدون اعتبار | نماینده‌ی **فعال** که Wallet Main دارد و `موجودی + سقف بدهی ≤ ۰` (هم‌قاعده با B5.1). نماینده‌ی بدون Wallet شمرده نمی‌شود (هشدار الکی برای نماینده‌ی تازه‌ساخته) |

**تفاوت آگاهانه با Reports ادمین:** سفارش‌های اکانت تست (`sales_channel=test_account`) در هیچ شمارشی نمی‌آیند؛ قیمتشان صفر است و «تعداد سفارش/نرخ شکست» را بی‌دلیل منحرف می‌کنند. مبلغ فروش و درآمد با Reports یکی می‌ماند.

## ED3. بازه و مقایسه
از `Resellers\Dashboard\DashboardPeriod` (امروز · ۷ روز · ۳۰ روز [پیش‌فرض] · این ماه · ماه گذشته)؛ بازه‌ی نیمه‌باز `[شروع، پایان)`، مرز طبق `APP_TIMEZONE`، بازه‌ی قبلِ هم‌طول، مقدار نامعتبر ⇒ پیش‌فرض.
درصد تغییر: `App\Support\PercentChange::of()` (عدد صحیح گردشده؛ **دوره‌ی قبل صفر ⇒ `null`** ⇒ UI «بدون مبنای مقایسه»، هرگز «∞٪»). این محاسبه از `ResellerSummary` بیرون کشیده شد؛ `ResellerSummary::percentChange` همان امضا را دارد و به آن ارجاع می‌دهد (رفتار بدون تغییر).

## ED4. صف رسید در انتظار
«رسیدهای در انتظار» = صفِ **پلتفرم**: خرید/شارژ فروشگاه اصلی (`reseller_id` خالی) و شارژ اعتبار خودِ نماینده (`wallet_owner_type=reseller`؛ تأییدش با ادمین اصلی است). شارژ کیف‌پول مشتریِ یک نماینده در صف خود نماینده است و در این عدد نمی‌آید؛ فقط به‌عنوان اطلاع «N رسید دیگر در صف نمایندگان» دیده می‌شود (`resellerQueuePendingPayments`).
رسید «کهنه» = در انتظار ≥ ۲۴ ساعت.
> توجه: نشان تعداد منوی «پرداخت‌ها» همچنان **همه‌ی** رسیدهای در انتظار را می‌شمارد (تغییر نکرد)؛ ممکن است از عدد داشبورد بیشتر باشد.

## ED5. «نیازمند توجه» (`alerts`)
مشتق از وضعیت زنده (ذخیره نمی‌شود). ترتیب: خطر ← هشدار ← اطلاع.
| کلید | لحن | شرط | مقصد (Channel) |
|---|---|---|---|
| `attention_orders` | خطر | سفارش `provision_failed` (همه‌ی زمان‌ها؛ پول گرفته، سرویس ساخته نشده) | سفارش‌ها با فیلتر `provision_failed` |
| `servers_down` | خطر | سرور فعال با `health_status=down` | فهرست سرورها |
| `pending_payments` | هشدار؛ **خطر** اگر رسید کهنه هست | رسید در انتظار صفِ پلتفرم | پرداخت‌ها با فیلتر `pending` |
| `resellers_out_of_credit` | هشدار | نماینده‌ی بدون اعتبار | فهرست نمایندگان |
| `servers_degraded` | هشدار | سرور فعال `degraded` | فهرست سرورها |
| `servers_full` | هشدار | سرور فعال با ظرفیت پر | فهرست سرورها |
| `open_tickets` | اطلاع؛ **هشدار** اگر اولویت بالا هست | تیکت `open` | تیکت‌ها با فیلتر `open` |
مبالغ در `ExecutiveAlert::$amounts` (Minor Unit) و متن با جانشین `{name}`؛ قالب‌بندی فقط در Channel (`renderBody`)، هم‌قاعده با M2 داشبورد نماینده.

## ED6. صفحه (Filament)
`App\Filament\Pages\Dashboard` (فیلتر «بازه‌ی زمانی» از URL/Session؛ هر ویجت با `DashboardPeriod::fromInput()` اعتبارسنجی می‌کند) با ۷ ویجت (`App\Filament\Widgets\Executive\*`) به این ترتیب:
1. `AttentionAlerts` — نیازمند توجه یا «همه‌چیز مرتب است».
2. `StatsOverview` — فروش (با تفکیک مستقیم/نمایندگی)، درآمد پلتفرم، سفارش‌ها (خرید/تمدید/میانگین)، کاربران جدید، سرویس‌های جدید، نرخ شکست؛ فلش و درصد تغییر.
3. `OperationsOverview` — وضعیت لحظه‌ای (مستقل از بازه): سرویس‌های فعال/رو‌به‌انقضا، کاربران و نمایندگان فعال، رسیدهای در انتظار، سرورها و مصرف ظرفیت، پیش‌پرداخت نزد پلتفرم، بدهی نمایندگان.
4. `RevenueTrendChart` — فروش و درآمد پلتفرم روزانه؛ همه‌ی روزهای بازه حاضرند؛ مجموع نمودار = مجموع KPI.
5. `ServerHealth` — سرورهای فعال: از کار افتاده ← کند ← پرمصرف‌ترین؛ حداکثر ۸.
6. `TopResellers` — ۵ نماینده‌ی برتر بازه بر پایه‌ی درآمد پلتفرم (سفارش، درآمد پلتفرم، سود نماینده).
7. `RecentOrders` — ۸ سفارش آخر (همه‌ی فروشگاه‌ها و وضعیت‌ها، بدون اکانت تست).
داشبورد پیش‌فرض Filament **جایگزین** شد، نه اضافه (`AdminPanelProvider` دیگر `Pages\Dashboard` را ثبت نمی‌کند).

## ED7. تغییر رفتار آگاهانه
- `SalesOverviewWidget` و `SalesChartWidget` (فقط «امروز/این ماه» و ۱۴ روز ثابت، با شش کارت) **حذف شدند**؛ جایگزین‌شان ویجت‌های بالاست با بازه‌ی قابل‌انتخاب و مقایسه. عددهای «فروش امروز/این ماه» با انتخاب بازه‌ی «امروز/این ماه» همان مقدار قبلی را می‌دهند (فروش بدون اکانت تست).
- کارت‌های «اکانت‌های فعال/کاربران فعال/پرداخت‌های در انتظار/تیکت‌های باز» به «وضعیت لحظه‌ای» و «نیازمند توجه» رفتند. «اکانت‌های فعال» اکنون غیرآزمایشی و «فعال در این لحظه» است (قبلاً هر `status=active` حتی منقضی‌نشده‌ی sync).
- «رسیدهای در انتظار» فقط صف پلتفرم است (ED4).
