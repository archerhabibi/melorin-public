# Admin Global Customer View Contract (B7.2)

> نسخه 1.1 · Parent: Master 2.8 / Website 1.9 / Reseller Customers 1.0 / Admin Executive Dashboard 1.0 · وضعیت: CANONICAL
> دامنه: فهرست و پرونده‌ی «کاربران و مشتریان» پنل ادمین پلتفرم (Filament، `/admin/users`).
> **بدون Migration، بدون Route جدید، بدون تغییر در Purchase/Provisioning/Refund/Wallet/Payment.** عملیات نوشتنیِ پیشین (ویرایش وضعیت/نام/موبایل و «تنظیم موجودی» Main) دست‌نخورده است و چیزی به آن‌ها اضافه نشده.

## GC1. Core: `Admin\Customers\GlobalCustomerDirectory` (فقط‌خواندنی)
- معادل سراسریِ `ResellerCustomerDirectory` (B5.2) ولی **بدون Scope به یک نماینده**: همه‌ی Userهای حذف‌نرم‌نشده، همه‌ی فروشگاه‌ها.
- **هیچ رکوردی نمی‌سازد/تغییر نمی‌دهد** (نه CustomerAccount، نه Wallet خالی، نه Audit). باز کردن فهرست/پرونده نباید در DB بنویسد (تست نگهبان + اسکن سورس برای فعل‌های نوشتن).
- ستون‌های محاسبه‌شده Subquery روی همان کوئری فهرست‌اند ⇒ تعداد کوئری فهرست **یک** است و به تعداد کاربر وابسته نیست؛ تعداد کوئری `summary()` و `profile()` هم به حجم داده وابسته نیست (تست).
- مبالغ `int` (Minor Unit)؛ Core هیچ Filament/Route/Money-format نمی‌شناسد (تست نگهبان).
- متدها: `query()`، `applySegment()`، `applyIdentity()`، `applyStore()`، `summary()`، `profile()`.
- `summary()` بدون `$now` صریح (مسیر پنل) در طول **یک Request** فقط یک بار محاسبه می‌شود (Instance در Container `scoped` است ⇒ بین Requestها/Jobها نشت نمی‌کند)؛ ویجت خلاصه و شمارنده‌ی تب‌ها دو بار کوئری سنگین نمی‌زنند. با `$now` صریح همیشه تازه است. `GlobalCustomerSummary::countFor(segment)` شمارنده‌ی هر بخش را از همان خلاصه می‌دهد.

## GC2. R2/R8 در عمل
`User` هویت مرکزی است ولی `CustomerAccount`ها **Merge نمی‌شوند**. پرونده هر فروشگاه را **جدا** نشان می‌دهد (عضویت، کیف‌پول، سفارش، خرج، سرویس فعال، درآمد پلتفرم). «جمع موجودی کیف‌پول‌ها» فقط نمایشی است و در متن صفحه صریحاً می‌گوید موجودی هر فروشگاه فقط در همان فروشگاه خرج می‌شود.

## GC3. تعریف‌ها (هم‌تعریف با B7.1)
| مفهوم | تعریف |
|---|---|
| سفارش قطعی | `paid` یا `account_created`، **بدون** `sales_channel=test_account` |
| خرج مشتری | `SUM(COALESCE(main_price, customers_price, 0))` — همه‌ی فروشگاه‌ها |
| درآمد پلتفرم از مشتری | `SUM(COALESCE(main_price, reseller_price, 0))` (در پرونده، به‌تفکیک فروشگاه) |
| فروشگاه سفارش | `orders.reseller_id` (خالی = اصلی) |
| عضو فروشگاه | `CustomerAccount` حذف‌نرم‌نشده با همان `scope_key` |
| سرویس فعال | `Account` غیرآزمایشی، `status=active`، بدون انقضا یا انقضای آینده — در همه‌ی فروشگاه‌ها |
| رو‌به‌انقضا | سرویس فعال با انقضا تا ۷ روز آینده (`ExecutiveDashboardService::EXPIRING_DAYS`) |
| سرویس تمام‌شده | `expired` یا `active` با انقضای گذشته (هم‌تعریف با `Account::scopeLapsed`) |
| موجودی Main | Wallet با `scope_key=main`؛ «موجودی نمایندگی‌ها» = جمع Walletهای دیگر (ممکن است منفی باشد) |
| تیکت باز | `tickets.status=open` |
| هویت Google | ردیف `user_identities` با `provider=google` |
| هویت یکپارچه | Google **و** `telegram_id` (پایه‌ی Single Identity، Website ↔ Telegram) |

اکانت تست (سفارش و سرویس) در هیچ شمارشی نمی‌آید (هم‌قاعده با ED2).

## GC4. بخش‌ها و فیلترها
- **بخش مشتریان** (`GlobalCustomerSegment`): `active_service` · `expiring` · `needs_renewal` (هیچ سرویس فعال ندارد ولی دست‌کم یکی تمام‌شده) · `never_bought` · `has_balance` (موجودی > ۰ در هر فروشگاه) · `multi_store` (≥ ۲ عضویت) · `open_ticket`.
- **هویت متصل** (`GlobalCustomerIdentity`): `google` · `telegram` · `google_and_telegram` · `email_verified` · `email_unverified` (ایمیل دارد، تأیید نشده).
- **عضو فروشگاه**: `main` یا `reseller:{id}`؛ فقط شکل `^(main|reseller:[1-9][0-9]{0,17})$` پذیرفته می‌شود (تا ۱۸ رقم؛ بیشتر از آن ⇒ بدون فیلتر).
- تعریف هر بخش/هویت **فقط** در Core است؛ شمارنده‌ی خلاصه و فیلتر جدول از همان می‌آیند (دو جا دو عدد نمی‌شود).
- هر مقدار نامعتبر (URL دست‌کاری‌شده) ⇒ **بدون فیلتر**، نه خطا و نه تزریق.
- **تب‌های سریع** (`ListUsers::getTabs()`): «همه» + یک تب برای هر بخش (`GlobalCustomerSegment::shortLabel()`)، با شمارنده‌ی `summary()->countFor()`. تب فقط `applySegment()` را صدا می‌زند؛ هیچ تعریف جدیدی در Channel نیست و با فیلتر «بخش مشتریان» ترکیب (AND) می‌شود. تب ناشناخته ⇒ تب «همه».
- فیلترهای پیشین «وضعیت» و «نقش» (نماینده/ادمین ربات/مشتری) بدون تغییر ماندند.

## GC5. فهرست (`UserResource`)
- ویجت خلاصه `UserResource\Widgets\GlobalCustomerSummary` (۸ کارت؛ در پوشه‌ی Resource، نه `Widgets/` پنل، تا روی داشبورد اجرایی نیاید): کاربران (+جدید ۳۰ روز، غیرفعال/مسدود)، سرویس فعال، رو‌به‌انقضا (+نیازمند تمدید)، پیش‌پرداخت نزد پلتفرم (+هنوز خرید نکرده)، عضو چند فروشگاه، تیکت باز، هویت یکپارچه (+Google/تلگرام)، صاحب نمایندگی.
- ستون‌ها: نام (+ایمیل/موبایل/تلگرام)، نقش، هویت متصل، فروشگاه‌ها، سرویس فعال، نزدیک‌ترین انقضا (شمسی + روز؛ هشدار تا ۷ روز)، موجودی Main (+ نمایندگی‌ها)، سفارش‌ها، مجموع خرید، آخرین خرید، تیکت باز، منبع عضویت، وضعیت، تاریخ عضویت (شمسی). همه‌ی ستون‌های عددی/تاریخ مرتب‌پذیرند.
- جست‌وجو: نام، ایمیل، موبایل، تلگرام، نام کاربری سایت. ستون‌های «سفارش‌ها/مجموع خرید» اکنون سفارش قطعی همه‌ی فروشگاه‌هاست (قبلاً `counts('orders')` همه‌ی وضعیت‌ها را می‌شمرد؛ ستون «تعداد اکانت» با «سرویس فعال» جایگزین شد).
- جست‌وجوی سراسری (B1.3) فقط رکورد کاربر را می‌خواهد و Subqueryهای فهرست را اجرا نمی‌کند.

## GC6. پرونده (`/admin/users/{id}`)
Infolist فقط‌خواندنی، همه‌ی داده از `profile()`:
1. **هویت**: نام، وضعیت، عضویت از + منبع، ایمیل (✓/✗ تأیید)، موبایل، نام کاربری، تلگرام، Google (ایمیل/آخرین ورود)، هویت یکپارچه، معرف، تعداد معرفی‌شده‌ها، نمایندگی.
2. **خلاصه‌ی فعالیت (همه‌ی فروشگاه‌ها)**: سفارش/تمدید، مجموع خرید، درآمد پلتفرم از مشتری، آخرین خرید، جمع موجودی، سرویس فعال/تمام‌شده، تیکت باز.
3. **فروشگاه‌ها** (اصلی اول، بعد بیشترین خرید): عضویت (`فعال/غیرفعال/مسدود/حذف‌شده/بدون عضویت`)، موجودی، سفارش، خرج، درآمد پلتفرم، سرویس فعال، آخرین خرید. فروشگاهِ بدون عضویت ولی دارای موجودی/سفارش هم می‌آید (ناهمخوانی دیده شود).
4. **سرویس‌ها** (تا ۵۰)، **آخرین سفارش‌ها** (۱۰)، **آخرین پرداخت‌ها** (۸)، **آخرین تراکنش‌های کیف‌پول** (۱۰؛ به‌تفکیک فروشگاه با مبلغ علامت‌دار و موجودی پس از تراکنش)، **تیکت‌ها** (۵) — هر کدام با فروشگاه.
5. **لینک پیمایشی** (فقط Channel؛ Route جدید نیست): شناسه‌ی سفارش/پرداخت/تیکت ← صفحه‌ی `view` همان Resource؛ برچسب فروشگاهِ نماینده ← ویرایش نماینده؛ معرف ← پرونده‌ی او؛ «نمایندگی» ← ویرایش نماینده. فروشگاه اصلی لینک ندارد.
- توضیح تراکنش از `WalletTransaction::publicDescription()` می‌آید؛ توضیح `referral_bonus` عمداً نمایش داده نمی‌شود (نام کاربر دیگری را دارد).
- **نمایش داده نمی‌شود:** `config_data`، `subscription_url/token`، `failure_reason` (علت داخلی Provisioning؛ جای آن B7.4 است) (تست نشت).
- کاربر حذف‌نرم‌شده ⇒ 404. کاربر بدون هیچ داده ⇒ صفحه با پیام‌های خالی رندر می‌شود.

## GC7. تغییر رفتار آگاهانه
- ستون «موجودی Main» از رابطه‌ی `wallet.balance` (یک کوئری به‌ازای هر ردیف) به Subquery رفت؛ نبودنِ Wallet ⇒ ۰ بدون ساخت Wallet.
- `UserResource::getEloquentQuery()` اکنون از Core می‌آید. `EditUser` و اکشن `adjustBalance` روی همان مدل کار می‌کنند؛ ستون‌های محاسبه‌شده هرگز نوشته نمی‌شوند (تست ذخیره).
- ستون نقش دیگر N+1 ندارد (`with('resellerAccount')`).
- (v1.1) `GlobalCustomerDirectory` در Container `scoped` ثبت شد (`AppServiceProvider`) و `GlobalCustomerSummary` فیلد `withBalance` گرفت (بخش «موجودی دارند» هم شمارنده‌ی تب دارد). `GlobalCustomerProfile` فیلد `recentWalletTransactions` گرفت؛ سازنده‌ی DTO فقط از Core ساخته می‌شود.

## GC8. تست
