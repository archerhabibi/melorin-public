# Customer Profile Contract (B3.5)

> نسخه 1.0 · Parent: Master 2.8 / Website 1.9 / Account Linking 1.0 / Session Security 1.0 / Customer Tickets 1.0 · وضعیت: CANONICAL
> دامنه: `GET|POST /profile` (`website[.store].identity.profile.{show,update}`) و «👤 حساب کاربری» در ربات اصلی. **تغییر Schema دارد** (P1).
> کارت‌های «روش‌های ورود»، «نشست‌های فعال» و «اتصال تلگرام» همان B2.4/B2.5 هستند و **تغییر نکردند**.

## P1. Schema

ستون جدید `users.full_name_edited_at` (timestamp، nullable). `NULL` = نام هیچ‌وقت دستی ویرایش نشده؛ همه‌ی کاربران موجود بدون backfill درست‌اند.
دلیل: وب‌هوک هر دو ربات تا B3.4 روی **هر پیام** `full_name` را با نام نمایشی تلگرام بازنویسی می‌کرد؛ هر نامی که مشتری در سایت (ثبت‌نام یا ویرایش) می‌گذاشت با اولین پیام ربات از بین می‌رفت.

## P2. لایه‌ها

| لایه | کلاس | نقش |
|---|---|---|
| Core | `Customer\ProfileCenterService` | `overview` (فقط‌خواندنی)، `update` (اعتبارسنجی + یکتایی + ذخیره + Audit)، `applyTelegramName` (قاعده‌ی نام تلگرام) |
| Core | `Customer\ProfileOverview` | DTO وضعیت (نام، ایمیل، موبایل، اتصال‌ها، تاریخ عضویت، چک‌لیست تکمیل) و برچسب‌های فارسی چک‌لیست (منبع واحد دو Channel) |
| Core | `Customer\ProfileCenterException` | خطای قابل‌نمایش با `field` (`full_name` \| `phone` \| `profile`) |
| Core (Support) | `App\Support\PhoneNumber` | نرمال‌سازی/نمایش موبایل (خالص، بدون وابستگی) |
| Website | `WebsiteProfileFacade` + `Identity\ProfileController` | فقط نوع/اندازه‌ی خام ورودی، تحویل به Core، نگاشت خطا به فیلد |
| Telegram | `Handlers\ProfileHandler` | متن/کیبورد/State مکالمه؛ همان Core و همان اعتبارسنجی |

Controller و Handler هیچ قاعده‌ی کسب‌وکاری ندارند. **یک اعتبارسنجی، یک نوشتن:** ویرایش از سایت و از ربات از یک مسیر Core می‌گذرد.

## P3. Profile = User، نه CustomerAccount

نام و موبایل یک بار برای Identity نگه‌داشته می‌شود و در Main و **همه‌ی** فروشگاه‌های نماینده یکی است (صفحه این را به مشتری می‌گوید).
`overview` و باز کردن صفحه **هیچ‌چیز نمی‌نویسد** (نه `CustomerAccount`، نه Audit) — همان اصل D4.1. «عضویت در این فروشگاه از» فقط از CustomerAccount **موجود** همین Context خوانده می‌شود.
Context فقط Route را تعیین می‌کند (`website.store.identity.profile.*`)؛ داده‌ی ذخیره‌شده Context ندارد.

## P4. فیلدهای قابل‌ویرایش (فهرست‌سفید)

فقط `full_name` و `phone`. هر فیلد دیگر در درخواست (`email`، `status`، `telegram_id`، `referrer_id`، `password`، `id`، ...) **نادیده** گرفته می‌شود.
ایمیل از این مسیر عوض **نمی‌شود** (Change Email = D-12، خارج از دامنه)؛ رمز/Google/Telegram/نشست‌ها = B2.4/B2.5. موبایل Proof هویت نیست (Master R9)، فقط اطلاعات تماس است ⇒ برای تغییرش رمز لازم نیست.

- **نام:** ۲..۱۰۰ نویسه؛ trim، فاصله‌های پیاپی ⇒ یکی؛ حذف نویسه‌ی کنترلی، صفر-عرض مخرب (ZWSP/ZWJ/BOM) و نویسه‌های جهت‌دهی دوطرفه (RLO و ...؛ Spoofing). **نیم‌فاصله‌ی فارسی (ZWNJ) می‌ماند.**
  حداقل یک «حرف»؛ `<` `>` و لینک (`http(s)://`، `www.`) رد می‌شود (نام در پنل ادمین، تیکت و ربات نمایش داده می‌شود).
- **موبایل:** اختیاری. ورودی با ارقام فارسی/عربی، فاصله/خط‌تیره/پرانتز، `+98…`، `0098…`، `98…`، `9…` ⇒ ذخیره‌ی `09xxxxxxxxx`؛ شماره‌ی خارجی فقط با `+` و ۸..۱۵ رقم (E.164). خالی ⇒ حذف شماره.
- **P4.1 یکتایی بی‌افشا:** شماره‌ی کاربر دیگر (حتی حذف‌نرم و با فرمت قدیمیِ ذخیره‌شده: `+98 912 …`، `0912-…`) ⇒ پیام عمومی «ثبت این شماره ممکن نیست…»؛ **هرگز** نمی‌گوید مال کیست (جلوگیری از User Enumeration). تصادم هم‌زمان (unique) هم همین پیام. شماره‌ی قدیمیِ خودِ کاربر با فرم متفاوت = «بدون تغییر».
- **P4.2 بدون تغییر = بدون اثر:** مقدار یکسان ⇒ هیچ نوشتن/Audit؛ فقط تغییر **نام** `full_name_edited_at` را می‌گذارد (تغییر موبایل نه).
- کاربر غیرفعال (`status != active`) ⇒ رد.
- ویرایش زیر قفل ردیف کاربر است (وب و ربات هم‌زمان روی هم نمی‌نشینند).
- **Audit:** `profile.updated` (Actor = همان User) با `after.fields` = فقط **نام فیلدها**؛ مقدار نام/موبایل (PII) هرگز ثبت نمی‌شود.

## P5. قاعده‌ی نام تلگرام (`applyTelegramName`)

نام نمایشی تلگرام فقط وقتی روی `full_name` می‌نشیند که نام «متعلق به تلگرام» باشد:

| وضعیت کاربر | نتیجه |
|---|---|
| `full_name_edited_at` پر است | **هرگز** بازنویسی نمی‌شود |
| ساخته‌شده از ربات (`joined_from` = `bot` / `reseller_bot`) و ویرایش‌نشده | دنبال تلگرام (رفتار قبلی حفظ شد) |
| ثبت‌نام‌شده از Website/Google که بعداً تلگرام وصل کرده و نام دارد | نام ثبت‌نامش می‌ماند |
| نام خالی | از تلگرام پر می‌شود |
| نام تلگرام خالی/فقط نویسه‌ی نامرئی | هیچ‌چیز پاک نمی‌شود |

هر دو وب‌هوک (ربات اصلی و ربات نماینده) از همین یک متد استفاده می‌کنند؛ متد فقط مدل را تغییر می‌دهد و Handler وب‌هوک `save()` می‌کند.

## P6. صفحه‌ی Website

- نمای کلی: درصد/چک‌لیست تکمیل (نام، موبایل، تأیید ایمیل)، یا نشان «پروفایل کامل است»؛ فرم نام + موبایل؛ ایمیل فقط‌نمایشی با نشان تأیید و لینک «تأیید ایمیل»؛ «عضو Melorin از» و «عضویت در این فروشگاه از» (شمسی)؛ نشان اتصال‌ها (رمز، Google، تلگرام).
- **چک‌لیست فقط موارد قابل‌انجام را می‌شمارد:** کاربر بدون ایمیل (ربات) «تأیید ایمیل» ندارد، چون افزودن ایمیل هنوز ممکن نیست (D-12).
- `POST /profile`: `auth` + `store.customer`، `throttle:10,1`، CSRF. خطا زیر همان فیلد (`full_name` / `phone`)، با حفظ ورودی؛ موفقیت: Redirect به Profile همان Context با پیام.
- Profile مستقل از تأیید ایمیل در دسترس است (Master G11).
- نام همیشه escape می‌شود (Blade)؛ هرگز HTML خام.

## P7. ربات تلگرام (فقط فروشگاه اصلی)

- «👤 حساب کاربری» از همان `overview` می‌خواند: شناسه‌ی تلگرام، نام، موبایل، ایمیل (+وضعیت تأیید)، تاریخ عضویت (شمسی + میلادی)، موجودی، و «برای تکمیل پروفایل: …» (از همان چک‌لیست و همان برچسب‌ها).
- دکمه‌های این‌لاین `profile:edit:name` / `profile:edit:phone` ⇒ State `PROFILE_AWAITING_NAME/PHONE` ⇒ پیام بعدی به همان `ProfileCenterService::update` می‌رود. `-` یا «حذف» در مرحله‌ی موبایل = حذف شماره.
- خطای ورودی ⇒ پیام خطای Core و **همان مرحله باز می‌ماند**؛ موفقیت یا بدون تغییر ⇒ State پاک و خلاصه‌ی تازه نمایش داده می‌شود.
- **زدن هر دکمه‌ی منوی اصلی از جریان ویرایش خارج می‌کند** (State مراحل Profile پاک می‌شود)؛ وگرنه متن آزاد بعدی به‌عنوان نام/موبایل ذخیره می‌شد. جریان‌های دیگر (پشتیبانی، شارژ، ...) دست نمی‌خورند.
- `callback` ناشناخته (`profile:edit:email` و ...) بی‌اثر است.
- ایمیل/رمز/اتصال‌ها از ربات ویرایش نمی‌شوند. ربات عمداً کاربر را به «ثبت‌نام در سایت و اتصال تلگرام» هدایت **نمی‌کند**: Merge وجود ندارد و تلگرامِ یک User ربات، با HMAC معتبر هم به User دیگر منتقل نمی‌شود (Account Linking L-قواعد؛ `owned_by_other`).

## P9. Out of Scope

Change Email (D-12)، افزودن Email به کاربر ربات (D-14)، تأیید موبایل با OTP (D-18)، آواتار/عکس پروفایل، ترجیحات اعلان (ایمیل/Push/تلگرام)، تغییر زبان/تقویم، حذف حساب، دانلود داده‌ها، نام نمایشیِ مجزا به‌ازای هر فروشگاه (`customer_accounts.display_name` فقط Snapshot زمان ساخت است و نمایش داده نمی‌شود)، Telegram Identity Bridge (T2)، ویرایش پروفایل در ربات نماینده (ربات نماینده صفحه‌ی «حساب کاربری» ندارد؛ فقط قاعده‌ی نام P5 روی آن اعمال می‌شود).
