# Customer Services Contract (B3.2)

> نسخه 1.0 · Parent: Master 2.8 / Website 1.9 / Customer Dashboard 1.0 · وضعیت: CANONICAL
> دامنه: مدیریت سرویس مشتری — `GET /accounts` (فهرست)، `GET /accounts/{id}` (جزئیات)، `POST /accounts/{id}/renew`،
> `POST /accounts/{id}/usage/refresh` (`website[.store].accounts.*`) و Job `accounts:sync-usage`.

## S1. اصل

Website فقط Channel است. منطق در Core است:

| لایه | کلاس | نقش |
|---|---|---|
| Core | `Customer\AccountManagementService` | تصویر سرویس (`ServiceOverview`)، پیش‌فاکتور، موجودی، تشخیص «ارسال دوباره»، تمدید |
| Core | `Renewal\RenewalService` (`quote()` + `renew()`) | تنها منبع قیمت و دروازه‌های تمدید؛ همان Order/Debit/Operation/Retry بند ۲۸–۳۹ |
| Core | `Customer\AccountUsageService` | هم‌گام‌سازی مصرف از پنل (Throttle، Job دوره‌ای) |
| Core | `Panels\SupportsUsageReport` | «استخراج مصرف از پاسخ پنل» دانش درایور است (Marzban، PasarGuard، Sanaei) |
| Website | `WebsiteServiceFacade` + `AccountsController` | نگاشت route→URL، متن فارسی، کلید Idempotency از توکن فرم |

ربات تلگرام در آینده (T3) می‌تواند از همان `AccountManagementService` بخواند.

## S2. «ارتقا / تغییر پلن» وجود ندارد

تصمیم صاحب پروژه: Service Management فقط **مشاهده‌ی مصرف + تمدید** است. تمدید همیشه روی **همان تعرفه‌ی فعلی** است؛
route، Core API و Audit برای تغییر پلن ساخته نشد (`ServiceManagementTest::there_is_no_upgrade_route_by_product_decision`).
اگر روزی لازم شد (از جمله «پرداخت فقط مابه‌التفاوت»)، یک تصمیم مالیِ جدا و Contract جدا می‌خواهد.

## S3. مصرف

- **S3.1** ستون `accounts.traffic_used_gb` تا B3.1 فقط هنگام ساخت/تمدید صفر می‌شد و هیچ‌جا از پنل خوانده نمی‌شد؛
  نوار مصرف و هشدار ۹۰٪ داشبورد همیشه روی صفر بود. از B3.2 مصرف از پنل خوانده می‌شود.
- **S3.2** ستون `accounts.usage_synced_at`: زمان آخرین هم‌گام‌سازی (مشتری می‌بیند عدد چقدر تازه است؛ Job می‌داند کدام‌ها قدیمی‌ترند).
- **S3.3** Job `accounts:sync-usage` هر ۱۵ دقیقه (`--limit=200`، `--older-than=30` دقیقه): فقط سرویس **فعالِ منقضی‌نشده**،
  قدیمی‌ترین‌ها اول (`null` اول)، سقف تعداد در هر اجرا تا پنل‌ها زیر بار نروند.
- **S3.4** دکمه‌ی «به‌روزرسانی مصرف» (فقط سرویس فعال): `throttle:12,1` روی route **و** ۱۲۰ ثانیه فاصله برای هر سرویس در Core
  (`Cache::add` اتمیک؛ دو درخواست هم‌زمان فقط یکی به پنل می‌رسد).
- **S3.5** شکست پنل یا پاسخ بدون فیلد مصرف ⇒ `FAILED` و **عدد قبلی دست‌نخورده** می‌ماند (هرگز صفر نمی‌شود).
- **S3.6** فقط‌خواندن از پنل + نوشتن دو ستون مصرف؛ هیچ تغییر مالی/وضعیتی ندارد.
- **S3.7** درایور بدون `SupportsUsageReport` ⇒ `UNSUPPORTED` (نه خطا). منبع مصرف: Marzban/PasarGuard `used_traffic`؛ Sanaei `up + down`.
- **S3.8** رنگ نوار: `Account::trafficTone()` — ≥۹۰٪ هشدار، ۱۰۰٪ خطر، نامحدود success؛ همان آستانه‌ی اعلان‌های داشبورد (`TRAFFIC_WARN_PERCENT`).

## S4. تمدید

- **S4.1 پیش‌فاکتور فقط‌خواندنی:** `RenewalService::quote()` هر دروازه‌ای را که `execute()` اعمال می‌کند می‌سنجد ولی Order/Debit/Wallet نمی‌سازد.
  مبلغ همان `customerDebit()` همان Context است (Rule 7: در فروشگاه نماینده `main_price` نقشی ندارد).
  UI مرز امنیتی نیست: `execute()` همه‌چیز را دوباره می‌سنجد.
- **S4.2 رفع باگ قیمت (B3.1):** پیش‌بررسی تمدید در سایت نماینده با `mainPrice()` سنجیده می‌شد، نه `customers_price`. اکنون `RenewalService::priceFor()` تنها منبع قیمت است (هم quote هم execute).
- **S4.3 دروازه‌ی وضعیت (رفع باگ):** فقط سرویس `active` یا `expired` تمدید می‌شود. `disabled` (مثلاً مسدودسازی نماینده)،
  `suspended` و بقیه با پرداخت «زنده» نمی‌شوند. دروازه هم در `quote()` و هم در `execute()` است (قبل از هر Debit).
- **S4.4 ریست کامل (بند ۲۸):** زمان (مبنا `max(اکنون، انقضا)`؛ روز باقی‌مانده نمی‌سوزد) + ترافیک؛ `usage_synced_at` همان لحظه ست می‌شود چون مصرفِ ریست‌شده دقیقاً صفر است.
- **S4.5 Idempotency:** فرم توکن یکتا می‌فرستد (S-07). ارسال دوباره‌ی همان توکن پس از تمدید موفق، موفقیت نشان می‌دهد
  (`isReplay`) و خطای «کمبود موجودی» جای آن نمی‌نشیند؛ چیزی دوباره کسر نمی‌شود.
- **S4.6 Throttle:** `POST renew` → `throttle:6,1` (قبلاً نداشت).
- **S4.7** پیام «برای تمدید، ابتدا کیف پول خود را شارژ کنید. هزینه‌ی تمدید: …» همان متن ربات/پیش از B3.2 است (اکنون با مبلغ درست).
- **S4.8** Refund/Retry کاملاً Admin-only؛ مشتری هیچ دکمه‌ای برای آن‌ها ندارد (مثل D4.3).

## S5. صفحات

- **فهرست:** هر سرویس یک کارت — نام تعرفه، انقضا/روز مانده، برچسب وضعیت، نوار مصرف (فقط سرویس فعال). سرویس منقضی دکمه‌ی «مشاهده و تمدید» دارد.
- **جزئیات:** مصرف (+ زمان آخرین هم‌گام‌سازی + دکمه‌ی به‌روزرسانی)، مشخصات، اطلاعات اتصال، کارت تمدید.
  کارت تمدید سه حالت دارد: **قابل تمدید** (مبلغ + موجودی + دکمه)، **کمبود موجودی** (مبلغ کمبود + «شارژ کیف‌پول»)، **غیرقابل تمدید** (دلیل؛ بدون فرم).
- **وضعیت‌ها:** `Account::displayState()` مرجع واحد برچسب است: `active` · `expiring` (≤ ۷ روز) · `expired` · `disabled` · `suspended`.
- **S5.1** باز کردن صفحه چیزی نمی‌نویسد (نه Wallet خالی، نه Order، نه هم‌گام‌سازی مصرف) — مثل D4.1.
- **S5.2** فقط `subscription_url` نمایش داده می‌شود، نه `config_data` (بند ۵۲).
- **S5.3** Context-isolation: مالکیت با `customer_account_id`؛ سرویس Main از فروشگاه نماینده 404 است و برعکس.

## S6. Out of Scope

ارتقا/تغییر پلن (S2)، Ticket Center (B3.4)، Wallet Center (B3.3)، نمودار تاریخچه‌ی مصرف، حذف/لغو سرویس توسط مشتری،
تغییر لینک اشتراک، اعلان Push/Email انقضا.
