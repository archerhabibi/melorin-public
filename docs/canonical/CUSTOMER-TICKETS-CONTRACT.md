# Customer Tickets Contract (B3.4)

> نسخه 1.0 · Parent: Master 2.8 / Website 1.9 / Customer Dashboard 1.0 / Wallet 1.0 · وضعیت: CANONICAL
> دامنه: `GET|POST /tickets…` (`website[.store].tickets.*`): فهرست، ثبت، گفتگو، پاسخ، بستن. **تغییر Schema دارد** (T1).

## T1. Schema و مالکیت

- ستون جدید `tickets.reseller_id` (nullable، FK به `resellers`، index `user_id+reseller_id+status`). `NULL` = فروشگاه اصلی.
  تمام تیکت‌های موجود (ثبت‌شده از ربات) بدون backfill درست `NULL` هستند.
- **مالکیت = `user_id + reseller_id`** (همان کلید Payment/Order). تیکتِ دیگران یا Context دیگر برای مشتری **وجود ندارد**: Website ⇒ **404** (نه 403).
- **T1.1 ربات:** ربات فقط فروشگاه اصلی است؛ `supportStart`/`resellerRequestStart`/`ticketReplySubmit` فقط تیکت‌های `reseller_id IS NULL` را می‌بینند.
  یعنی تیکت باز در فروشگاه نماینده ربات را به «ادامه‌ی همان تیکت» نمی‌برد، و تیکتِ Main ثبت‌شده در سایت با ربات یکی است (پل هویت T2).
- `reseller` حذف شود ⇒ `nullOnDelete` (هم‌الگو با Order/Payment): تیکت‌هایش به فروشگاه اصلیِ **همان کاربر** برمی‌گردد، نه کاربر دیگر.

## T2. لایه‌ها

| لایه | کلاس | نقش |
|---|---|---|
| Core | `Customer\TicketCenterService` | فهرست، یافتن با مالکیت، `open` / `reply` / `close`، شمارنده‌ها، پاک‌سازی ورودی |
| Core | `TicketCounts`, `TicketCenterException` | DTO و خطای قابل‌نمایش |
| Website | `WebsiteTicketFacade` + `Account\TicketsController` | اعتبارسنجی ورودی، تحویل به Core، نگاشت URL |

Controller هیچ شرط کسب‌وکاری ندارد؛ ربات (T3) می‌تواند از همان Core بخواند.

## T3. وضعیت‌ها

`open` «در انتظار پاسخ پشتیبانی» ←(ادمین پاسخ)→ `answered` «پاسخ داده شد» ←(مشتری پاسخ)→ `open`. `closed` «بسته شده» **نهایی** است:
مشتری تیکت بسته را باز نمی‌کند (تیکت جدید می‌سازد)؛ ادمین پنل هم همین را (`isOpen`). پاسخ مشتری به `answered` آن را `open` می‌کند.
بستن idempotent است. فقط تیکت `support` توسط مشتری ساخته می‌شود؛ `reseller_request` (ربات) در فهرست دیده و پاسخ داده می‌شود.

## T4. ثبت و پاسخ

- موضوع ۳..۱۰۰، متن ۵..۴۰۰۰ نویسه (پاسخ ≥ ۲)؛ آرایه/نوع غلط ⇒ خطای اعتبارسنجی. کاراکترهای کنترلی حذف و ابتدا/انتها trim می‌شود.
- **T4.1 سقف:** حداکثر `MAX_OPEN = 5` تیکت غیر بسته در هر فروشگاه به‌ازای هر کاربر (قفل ردیف کاربر ⇒ دو درخواست هم‌زمان هر دو رد نمی‌شوند). بستن یک تیکت جا باز می‌کند.
- **T4.2 دوبار-کلیک:** همان موضوع+متن (یا همان پاسخ) در `DUPLICATE_WINDOW_SECONDS = 30` ⇒ همان رکورد، نه تکراری و بدون رویداد دوم.
- Throttle: ثبت ۵/دقیقه، پاسخ و بستن ۱۰/دقیقه.
- **T4.3 رویدادها:** `TicketCreated` / `TicketUserReplied` همان رویدادهای ربات‌اند ⇒ اطلاع به ادمین بدون تغییر. انتشار **best-effort** است:
  خرابی Listener (ربات/شبکه) فقط Log می‌شود؛ تیکت ثبت‌شده است و مشتری 500 نمی‌بیند.
- اطلاع ادمین برای کاربر بدون تلگرام، ایمیل را نشان می‌دهد و برای تیکتِ نماینده «فروشگاه نماینده: #id» دارد. ستون «فروشگاه» به جدول تیکت‌های پنل اضافه شد.

## T5. نمایش و حریم خصوصی

- **T5.1** نام واقعی ادمین هرگز به مشتری نشان داده نمی‌شود: «پشتیبانی» / «شما» (`TicketMessage::customerLabel()`؛ `senderLabel()` فقط پنل ادمین).
- **T5.2** متن تیکت و موضوع همیشه escape می‌شود (Blade)، خط‌های جدید با CSS حفظ می‌شود؛ هرگز HTML خام.
- فهرست: «پاسخ داده شد» بالاتر، بعد جدیدترین فعالیت؛ فیلتر وضعیت با لینک GET (مقدار نامعتبر ⇒ همه)؛ تاریخ‌ها شمسی (هم‌الگو با Wallet).
- باز کردن صفحه‌ها هیچ چیزی نمی‌نویسد (نه تیکت، نه CustomerAccount).

## T6. داشبورد

اعلان `ticket.answered` (info) از تعداد تیکت `answered` همین Context: یک تیکت ⇒ لینک مستقیم به همان تیکت (`TARGET_TICKET`)، چند تیکت ⇒ فهرست (`TARGET_TICKETS`).
مشتق از وضعیت زنده است؛ با پاسخ یا بستن خودبه‌خود ناپدید می‌شود. آیتم «پشتیبانی» به منوی حساب اضافه شد.

## T7. Out of Scope

پیوست فایل (ستون `attachment` هست ولی UI ندارد)، اطلاع‌رسانی ایمیلی/Push به مشتری هنگام پاسخ (فعلاً فقط تلگرام برای کاربرِ متصل + اعلان داشبورد)،
تیکت‌های مدیریت‌شده توسط نماینده (پنل نماینده، B5)، دسته‌بندی/اولویت انتخابی مشتری، امتیازدهی، باز کردن مجدد تیکت بسته،
جستجوی متنی در تیکت‌ها، Auto-close تیکت‌های قدیمی، نشان «خوانده‌نشده» ماندگار (نیاز به ستون `customer_read_at`).
