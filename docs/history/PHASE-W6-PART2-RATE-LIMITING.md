# فاز W6 (بخش دوم) — Rate Limiting (v3.2.7)

مرجع: `ROADMAP-WEBSITE-v1.md` فاز W6 بند ۱ + جدول دقیق بخش ۹.۶.

## وضعیت قبل از این پچ (Audit سریع)

| مسیر | عدد مورد نیاز (بخش ۹.۶) | وضعیت قبل از پچ |
|---|---|---|
| Login | ۵/دقیقه به‌ازای IP+شناسه | ✅ از قبل درست بود — `LoginRequest::throttleKey()` (پچ W1) دقیقاً `email\|ip` را کلید می‌کند. کاری لازم نبود. |
| Checkout/Purchase | ۱۰/دقیقه به‌ازای IP | ✅ از قبل `throttle:10,1` روی همه‌ی مسیرهای مرتبط (پچ‌های ۳.۲.۱ تا ۳.۲.۴) بود. |
| Upload رسید | ۵/دقیقه | ❌ به اشتباه `throttle:10,1` بود (پچ ۳.۲.۲، قبل از مستندشدن این عدد دقیق در بخش ۹.۶). |
| Reset رمز | ۳/ساعت **به‌ازای ایمیل** | ❌ فقط `throttle:3,60` سطح Route بود که IP را کلید می‌کند، نه ایمیل را — یعنی یک مهاجم با چند IP می‌توانست ایمیل قربانی را بیشتر از حد مجاز Bombing کند. |

این پچ فقط دو مورد ❌ را اصلاح کرد؛ دو مورد ✅ دست‌نخورده ماندند.

## تغییرات

- `routes/website.php`: `wallet.receipt.store` از `throttle:10,1` به
  `throttle:5,1`.
- `PasswordResetLinkController::store`: همان الگوی دقیق
  `LoginRequest::throttleKey()` تکرار شد (`RateLimiter::tooManyAttempts`/
  `hit`/`availableIn`)، با این تفاوت که کلید **فقط `email`** است (بدون
  IP) — چون بند ۹.۶ دقیقاً «به‌ازای ایمیل» گفته، نه «ایمیل+IP» (برخلاف
  Login که صراحتاً هر دو را خواسته). محدودیت `throttle:3,60` سطح Route
  هم دست‌نخورده باقی ماند — یک لایه‌ی دفاعی اضافه (per-IP)، نه
  جایگزین.

## چرا Login و Checkout دست نخوردند

Audit نشان داد هر دو از قبل درست بودند؛ تغییردادن چیزی که کار می‌کند
بدون دلیل، خودش ریسک است (می‌تواند رفتار تست‌شده را بشکند). فقط
مواردی که واقعاً با بخش ۹.۶ مغایرت داشتند اصلاح شدند.

## تست

`tests/Feature/Website/RateLimitingTest.php`:
- Reset رمز: نفر چهارم درخواست همان ایمیل رد می‌شود.
- Reset رمز: ایمیل دیگری (حتی از همان IP) مسدود نیست — تایید می‌کند
  محدودیت واقعاً per-email است، نه per-IP.
- Upload رسید: ششمین تلاش در یک دقیقه با ۴۲۹ رد می‌شود.

## محدودیت این پچ

بدون PHP اجرا‌پذیر نوشته شده:

    php artisan test --filter=RateLimitingTest

نکته‌ی مهم برای اجرای واقعی: تست‌های Rate Limit به Cache Driver درایور
پیش‌فرض تست (`array`، sync بین درخواست‌های همان تست) وابسته‌اند؛ اگر
پروژه در تست از یک Cache Driver متفاوت (مثلاً Redis مشترک بین
Workerهای موازی) استفاده کند، این تست‌ها باید ایزوله اجرا شوند وگرنه
باقی‌مانده‌ی Rate Limit تست قبلی روی تست بعدی اثر می‌گذارد.
